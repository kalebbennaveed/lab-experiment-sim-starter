# Replace the nominal method with your algorithm

Start with [double_integrator_method.py](double_integrator_method.py). It is a
working example in which a method returns double-integrator acceleration
commands, and the supplied adapter generates the reference for the
flatness and geometric controller.

```text
Your method: u = [ax, ay, az]
          ↓ held between method updates
Double integrator: p_dot = v, v_dot = u
          ↓ desired [p, v] and u
Flat-state conversion
          ↓ position, velocity, acceleration, heading, angular feedforward
Geometric controller
          ↓ four motor speeds
Quadrotor dynamics
          ↓ measured position/velocity available to your method
```

## Run and preview the example

Run these commands from the repository root:

```bash
uv sync --locked
uv run python examples/double_integrator_method.py --output outputs/my_method.json
uv run lab-demo --example examples/double_integrator_method.py --port 8001 --open
```

The browser opens at **http://127.0.0.1:8001**. Save edits to the method while
the preview is running to recompute the flight. If an edit fails, the browser
shows the error and keeps the previous successful run visible.

For a trajectory anywhere in free space, use the generic configuration:

```bash
uv run python examples/double_integrator_method.py --config config/generic.toml
uv run lab-demo --example examples/double_integrator_method.py --config config/generic.toml --port 8001 --open
```

The lab configuration checks the Flylab boundaries; the generic configuration
disables them. Boundary checks report crossings rather than preventing them.

## Implement your method

Copy the example to `examples/my_method.py`. Replace the marked block in
`MyAccelerationMethod.__call__` with your solver, policy, or planner. Its
contract is:

```python
def __call__(self, t, planned_state, measured_state):
    # Compute your world-frame translational acceleration here.
    acceleration = your_algorithm(t, planned_state, measured_state)
    return np.asarray(acceleration, dtype=float) # shape (3,)
```

| Value | Meaning | Units / shape |
| --- | --- | --- |
| `t` | Current simulation time | seconds |
| `planned_state` | The virtual DI reference generated by previous commands | `[px, py, pz, vx, vy, vz]`, shape `(6,)` |
| `measured_state` | The current quadrotor position and velocity | same six-state layout |
| Returned `u` | Translational acceleration command | `[ax, ay, az]`, m/s², shape `(3,)` |

Use `planned_state` for a method that evolves a planned trajectory. Use
`measured_state` when your method needs physical vehicle feedback; it includes
tracking error, motor lag, and disturbances. The method receives copies, so
editing its inputs does not mutate the simulator or reference.

All vectors use the **world frame with z up**. The DI command is net
translational acceleration: **do not add gravity, mass, thrust, or motor units**.
For a stationary hover reference, `u = [0, 0, 0]`; the downstream flatness and
geometric controller add gravity compensation. Return finite values. Set
acceleration limits inside your method if it needs them; the example's
per-axis clipping is a demonstration setting.

The working method uses a Lissajous curve as its task goal and a simple PD law
to control the virtual double integrator. Keeping that goal lets you compare
methods on the same task. You can change the goal as well as the method.

## How acceleration becomes a tracking reference

`DoubleIntegratorPolicy` holds the previous acceleration command and advances
the desired six-state with the exact constant-acceleration equations:

```text
p_next = p + dt*v + 0.5*dt²*u
v_next = v + dt*u
```

At each geometric-controller step, it passes the current desired position,
velocity, and acceleration through `double_integrator_reference`, which calls
the `flat_state_to_reference` conversion. The low-level
controller and quadrotor plant then track that reference.

In the example, the method updates every `5*config.simulation.dt`: 20 Hz with
the default 0.01 s simulation step. The reference, flatness conversion, and
geometric controller update at 100 Hz. Choose `command_dt >= simulation.dt`
and an integer multiple of that step. Other intervals update on the first
simulation sample at or after the requested time. Method calls are synchronous;
simulation time is fixed even if a solver takes longer to compute.

`make_initial_reference` supplies the desired initial position/velocity
separately. This lets the stateful method's first call observe the initialized
quadrotor, including `simulation.initial_position_error`. The adapter starts
its DI reference at that same desired state and retains it between updates.
Each simulation or live-preview rerun creates a new method and adapter.

The flat-state conversion assumes zero jerk and snap and
defaults to yaw `3*t/8`. The position and velocity rollout still follows the
acceleration commands supplied by your method.

## If your planner already returns a trajectory

A planner such as MPC may already produce desired position, velocity, and
acceleration. In that case, sample its planned trajectory and convert the
sample directly. You do not need to integrate those states again:

```python
import numpy as np

from lab_sim import double_integrator_reference

class MyTrajectoryPolicy:
    def __init__(self, config, planner):
        self.config = config
        self.planner = planner

    def __call__(self, t, state):
        measured = np.concatenate((state.position, state.velocity))
        # Implement sample() in your planner. Interpolate its desired states
        # consistently with the held DI acceleration between planner samples.
        desired_di_state, acceleration = self.planner.sample(t, measured)
        return double_integrator_reference(
            desired_di_state, # [px, py, pz, vx, vy, vz], shape (6,)
            acceleration,     # [ax, ay, az], shape (3,)
            gravity=self.config.vehicle.gravity,
            yaw=self.config.trajectory.yaw + self.config.trajectory.yaw_rate*t,
            yaw_rate=self.config.trajectory.yaw_rate,
        )
```

Pass this policy to `simulate(config, policy=policy,
initial_reference=initial_reference)` to choose the vehicle's desired initial
state independently of the planner. For command-line/live-preview use, wire
your policy factory and initial-reference factory into `example_main`, as the
worked example does. Both paths feed the same flatness conversion, geometric
controller, and physical dynamics.

## Check what the results measure

The orange path in the web demo is **the reference produced by your method**;
the green path is the physical quadrotor flight. RMS, maximum, and final errors
measure the vehicle's ability to track that generated reference. They do not
measure how closely your planned reference follows the original task goal.
Evaluate your method against its goal, constraints, and computation budget
separately if those are the quantities you are comparing.

For the supplied example, these commands export the baseline and your method
on the same lab task:

```bash
uv run python examples/lab_demo.py --output outputs/baseline.json
uv run python examples/my_method.py --output outputs/my_method.json
uv run pytest
```

The JSON exports the desired DI positions (`history.reference`), desired
velocities (`history.reference_velocity`), and your acceleration commands
(`history.reference_acceleration`) at the configured output sampling rate.
Set `simulation.sample_dt = simulation.dt` to export every controller step.
It also contains actual positions/velocities, rotations, motor speeds, errors,
and optional boundary diagnostics. The main
[repository README](../README.md) describes the models and conventions.
[custom_policy.py](custom_policy.py) is a smaller example for changing
a reference directly.
